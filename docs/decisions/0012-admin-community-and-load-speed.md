# 0012 管理后台、社区内容和加载速度

- 状态：已上线（2026-11-10）。市场页偶尔的亚秒级停顿还没查清，见第 4 节末尾。
- 用户的要求（2026-11-09）：继续优化界面和加载速度，完善管理后台和用户社区的内容。（同一次要求里的 MCP、CLI 和 agent 接入见 0011。）

## 背景

- 管理后台（0009 第 7 节）只有一页：确认积分订单、加减积分、一张用户表。用户一多就翻不动，也看不到站点在不在正常跑、内容有没有问题。
- 社区栏目（0005）整个建在链上。线上还没有配链（`MOTIF_CHAIN_RPC_URL` 是空的），所以「社区」点进去只有一句「社区暂时不可用」，而站上明明已经有人、有公开仓库。
- 市场从 175 个条目加到 425 个之后，线上按请求渲染的页面（市场、定价、排行、社区）不定时地卡住：多数请求 0.1–0.25 秒，隔一阵就有一次 2–23 秒。

## 决定

### 1. 管理后台分成五栏

`/admin` 下：概览、用户（`/users`、`/users/<id>`）、积分订单（`/orders`）、商店订单（`/store`）、内容（`/content`）。查询都在 `lib/accounts/admin.ts`，页面共用的表格、分段筛选、翻页在 `components/admin/ui.tsx`。

- **概览**：全站的数、近 14 天的走势（新用户、收款、条目的使用）、等着确认收款的订单、加减积分、系统状态（邮件、GitHub 登录、工作台运行器、截图、链、数据库大小、目录条目数、管理员人数）。系统状态只显示「配了没有」，不显示配置的值；管理员名单只数数，邮箱不出函数。
- **列表都分页、筛选条件都在地址里**：能收藏、能后退，不用客户端状态。页码超出范围时拉回最后一页。
- **后台的时间一律按北京时间**（`lib/site.ts` 的 `SITE_TIME_ZONE`）。服务器是 UTC，管理员在国内；按服务器时区显示的话，「今天的订单」会差八小时，走势图的一天也切在早上八点。用户自己的流水页也用同一个时区，两边对账时看到的是同一个时刻。
- **数据库大小按页数算**（`PRAGMA page_count × page_size`），不看主文件：WAL 模式下刚写的数据还在 `-wal` 里，主文件可能只有一页。
- **商店订单只读**：买家、扣的积分、状态都列出来。定制单失败时的退款是自动的（0008），后台不另做手动退款；要补偿用户，用「加减积分」并写原因，流水里查得到。

### 2. 下架是一把锁，不只是改成私有

内容栏可以下架公开仓库。只把它改成私有的话，作者点一下又公开了，等于没下架。所以：

- `repo` 表加一列 `taken_down_at`。下架 = 改成私有 + 记下时间；恢复 = 改回公开 + 清掉时间。文件不动，`updated_at` 也不动（那是内容的更新时间，恢复后它应该回到列表里原来的位置）。
- 下架中的仓库，作者自己还看得到，但不能改回公开、不能被 fork；仓库页上写明「已被下架」和原因去哪问。
- 管理员能打开下架中的仓库（要看了才能决定恢复不恢复），但**不能**打开作者自己设成私有的仓库：巡查管的是所有人看得见的东西。
- 已知的限制：作者可以把同样的文件再传成一个新仓库。要拦这个得按内容哈希记黑名单，现在的量用不上；出现了再做，届时处理的是账号而不是仓库。

### 3. 社区首页不依赖链

社区栏目分成两半：

- **不依赖链的**：首页（`community/(hub)`）、发现（`/community/explore`：公开仓库的搜索和排序）、创作者（`/community/creators`）。数据全部来自已有的 `repo`、`profile`、`item_stat_daily`，查询在 `lib/repos/explore.ts`，**不加表、不加迁移**。
- **依赖链的**：投稿、评审、治理、链上作品。没配链时这几页照旧显示「暂时不可用」，社区的导航里也不摆它们，不留点进去是空白的链接；配了链，链上的概览排在首页前面，站内的分区接在后面。

规则：

- 在社区里露出的仓库 = 公开而且里面有文件。空仓库点进去没有东西可看。首页的数字、列表、搜索用同一个条件，数才对得上。
- 创作者按「被 fork 的次数 → 公开仓库数 → 最近活跃」排。被别人拿去用最能说明东西有用；刚起步、还没人 fork 的站点按仓库数排，不会是一张全零的榜。
- 搜索用 `LIKE`（转义 `%`、`_`），词数、长度和每页条数都有上限。现在的量不需要全文索引；仓库到了几万个再换 FTS5。

### 4. 目录在进程里只解析一次

**现象**（2026-11-09，在服务器上绕过 Caddy 直接请求站点容器）：`/robots.txt` 一直是 3–15 毫秒；`/pricing` 多数时候 0.1–0.25 秒，但隔一阵出现一次 2.6、5.4、14.6、23.1 秒。卡的时候同机另一个进程的 CPU 测试照常，说明是站点进程自己在忙，不是网络、Caddy 或者整机负载。

**根因**：`catalog.json` 里有每个条目的全部源码，425 个条目时是 12 MB。页脚要显示目录的生成日期，于是每个按请求渲染的页面都会 `getCatalog()`；React 的 `cache()` 只在一次渲染里去重，路由处理里根本不生效。结果是每个请求都把 12 MB 重新读、重新解析一遍。在线上容器里实测，光这一步是 130–480 毫秒，八次里有一次 3 秒（本机 45 毫秒）；解析出来的几十 MB 对象用完就是垃圾，回收时整个进程停住，这就是那些几秒到二十几秒的卡顿。条目从 175 加到 425 之后才明显起来。

**决定**（`apps/web/src/lib/catalog.ts`）：

- 解析好的目录在进程里留一份（挂在 `globalThis` 上，理由同 `lib/community/state.ts`），用文件的修改时间和大小做钥匙。线上文件不变，只解析一次；开发时预览沙箱重新构建换了文件，下一个请求就读到新的。
- 留下的这份所有请求共用，所以**整个冻结**。谁原地改了它（排序、加字段），当场报错，而不是悄悄影响别的请求。现有代码里要改的地方都是先拷贝再改（工作台的 `remixItem`、各处的 `[...].sort()`），冻结之后跑过一遍：市场、条目页、排行、社区、`/r/` 和 `/skill/`、agent 工具、CLI 下单取代码、从条目开工作台会话。
- 读失败不留缓存。沙箱写文件不是原子的，读到写了一半的会解析失败，下一个请求重读。
- 文件还不存在时（沙箱第一次构建没跑完）也不留，照旧给空目录。

**顺带**（`lib/media.ts`）：市场页每次请求要给每个条目查 4 个媒体文件在不在，425 个条目就是 1700 次同步的文件系统调用。线上的 `public/` 是打进镜像的，不会变，所以第一次用到时把 `public/media/` 列一遍记下来；开发时 `pnpm capture` 随时会生成新文件，仍然每次现查。

**本机的前后对比**（生产构建 `next start`，每个地址连续请求 40 次，中位数 / 95 分位，毫秒；改前改后页面的文字和媒体地址逐一比过，完全一样）：

| 地址 | 改前 | 改后 |
| --- | --- | --- |
| `/pricing` | 87 / 109 | 20 / 34 |
| `/rank` | 146 / 176 | 22 / 40 |
| `/community` | 93 / 127 | 27 / 34 |
| `/market` | 104 / 128 | 54 / 69 |
| `/r/border-beam.json` | 147 / 252 | 3 / 16 |
| `/api/agent/search_ui?query=loader` | 76 / 100 | 6 / 17 |

本机的解析只要 45 毫秒，线上是它的 3–10 倍，所以线上省下的会更多；市场页剩下的 50 毫秒是渲染 425 张卡片本身。

**取舍**：

- 多占一份常驻内存（实测堆上约 20 MB）。换来的是每个请求少 100–500 毫秒的 CPU 和几十 MB 的垃圾，值。
- 冻结之后，以后谁写了原地修改目录的代码会直接报错。这是故意的。

**考虑过、没有做的**：

- 把这些页面改成静态的或者定时再生成：它们按请求读的是真东西（定价读环境变量里的单价，市场读查询参数，社区和排行读数据库），改了就要另想办法让数据不过期。先把每个请求都在白做的事去掉。
- 把目录拆成「小索引 + 每个条目一个文件」：从根上更干净，但要动目录的构建和所有读它的地方。留一份在内存里已经把问题消掉了；目录涨到一百 MB 上下、内存成了问题再拆。
- 只把客户端组件用到的翻译传给浏览器（现在每页都带全部文案，压缩后十几 KB）：要逐个组件核对用了哪些命名空间，漏一个就是线上报错，收益比不上风险。
- 国内 CDN 或者更好的线路：不是代码的事，要用户定。

**线上复测**（2026-11-10，部署前后各量一次；在服务器上直接请求站点容器，每个地址连续 40 次，毫秒）：

| 地址 | 部署前：中位数 / 最慢 / 超过 1 秒的次数 | 部署后 |
| --- | --- | --- |
| `/robots.txt` | 9 / 284 / 0 | 4 / 59 / 0 |
| `/pricing` | 732 / 55242 / 19 | 17 / 27 / 0 |
| `/market` | 475 / 14148 / 12 | 78 / 5630 / 3 |
| `/rank` | 没量 | 26 / 305 / 0 |
| `/community` | 没量 | 31 / 211 / 0 |
| `/r/border-beam.json` | 没量 | 6 / 86 / 0 |

几秒到几十秒的卡顿没有了，定价、排行、社区和 `/r/` 都回到了几十毫秒以内。

**还剩下的**：市场页偶尔还有 0.3–1.6 秒的请求（上表那次有 3 个 4–5 秒的，是构建刚结束三分钟时量的，之后没再出现）。换成每个地址连续请求 20 秒来数超过 200 毫秒的请求：`/robots.txt` 1320 次里 0 个；`/pricing` 439 次里 7 个，最慢 0.5 秒；`/rank` 172 次里 6 个，最慢 0.8 秒；`/market` 179 次里 18 个，最慢 1.2 秒。只有真的在渲染页面时才出现、渲染得越重越多，看起来是渲染本身产生的垃圾在这台慢机器上回收时的停顿，但**没有确认**（没有开 GC 日志）。要继续的话，先在线上开一次 `--trace-gc` 确认，再决定是减少市场页每次请求渲染的东西，还是把默认查询的结果缓存起来。
