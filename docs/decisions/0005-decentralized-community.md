# 0005 去中心化社区：链上登记、策展审核与 DAO 治理

- 状态：合约和站点接入已实现并通过测试（2026-10-08）；**未部署到任何公开网络**，部署链、代币分配和法律评估待定
- 验证：
  - `pnpm --filter @motif/contracts test`：Solidity 单元 / 模糊 / 不变量测试、Ignition 部署与事件索引集成测试、内容哈希单元测试；
  - `apps/web/test/community.test.ts`：投稿检查、托管文字、提案解码；
  - `e2e/community.spec.ts`：钱包、投稿、审核、上架、链上验证、治理全流程，跑在独立的本地链上。
- 代码：`packages/contracts`（合约、部署、事件归约器）、`apps/web/src/lib/community` 和 `apps/web/src/components/community`（站点）

## 背景

用户决定把 Motif 从“维护者整理的素材站”变成去中心化社区：任何人都可以投稿，由社区审核；署名和 Remix 谱系可以追溯；用代币做激励和 DAO 治理。用户的选择：

| 问题 | 选择 |
| --- | --- |
| 技术路线 | Solidity / EVM 兼容，部署链以后再定 |
| 资金流 | 社区代币 + DAO 治理 |
| 上链范围 | 条目注册与版本、Remix 谱系与署名、社区策展与审核、创作者身份与声誉 |
| 源码存储 | 站点自托管，链上只存哈希 |

## 决定

### 1. 链上只放事实和哈希，不放内容

| 上链 | 不上链（站点托管，链上存 sha256） |
| --- | --- |
| slug、维护者、版本号、内容哈希、许可证 | 条目源码（ItemSource） |
| 上游仓库与固定 commit（写在事件里） | 海报、循环视频 |
| Remix 的父条目和父版本 | 创作者资料 JSON（头像、简介、链接） |
| 审核票、结果、押金、奖励、罚没 | 审核意见全文 |
| handle、资料哈希、声誉 | |

- 源码上链既贵又删不掉，而站点必须能按法律要求下架内容。
- 用 IPFS / Arweave 托管会依赖外部网关，违反“不依赖外部 CDN”的原则（AGENTS.md 第 4 条）。
- 站点托管仍然可以验证：任何人下载站点给的源码、重算哈希，就能发现站点是否篡改了社区审核通过的代码。

### 2. 六个合约，依赖单向

| 合约 | 职责 | 管理员 |
| --- | --- | --- |
| `MotifToken` | ERC-20 + Permit + Votes（时间戳时钟），总量上限 10 亿，只有时间锁能增发 | 时间锁（owner） |
| `MotifGovernor` | OpenZeppelin Governor：可调参数、简单计票、按比例的法定人数、晚到法定人数自动延长、时间锁执行 | 自身（改参数要走提案） |
| `MotifTimelock` | DAO 的金库和执行者，提案通过后排队，延迟到期才执行 | 自身 |
| `MotifRegistry` | 条目登记簿：slug、维护者、版本（内容哈希、许可证、作者、状态）、Remix 谱系、下架状态 | 时间锁 |
| `MotifCuration` | 投稿入口：押金、审核投票、结算（退押金、奖励、罚没、声誉） | 时间锁 |
| `MotifIdentity` | handle、资料哈希、不可转让的声誉 | 时间锁 |

`Curation` 依赖 `Registry`、`Identity` 和代币；`Registry` 和 `Identity` 不知道 `Curation` 的存在，只认角色（`CURATION_ROLE`、`ISSUER_ROLE`）。将来要换审核机制（例如改成代币加权投票），只需部署新的 `Curation`，再由 DAO 把角色转过去，登记簿和声誉数据都不用动。

### 3. 权限结构

| 角色 | 持有者 | 能做什么 |
| --- | --- | --- |
| 管理员 | 时间锁 | 调参数、改许可证白名单、任免审核员和版主、增发、动用金库、裁定进行中的审核 |
| 提案 / 取消 | 治理合约（唯一） | 向时间锁提交通过的提案 |
| 执行 | 任何人 | 执行延迟已到期的提案 |
| 版主 | 应急多签（DAO 可撤换） | 下架和恢复条目、封禁冒充的 handle、在垃圾投稿潮时暂停新投稿 |
| 审核员 | DAO 任免，创世审核员在部署时指定 | 对投稿投票 |
| 部署者 | 无 | 部署结束后不持有任何角色，测试覆盖了这一点 |
| seeder | 创世导入用的地址 | 临时持有 `CURATION_ROLE` 导入现有条目，完成后自行放弃 |

版主单独存在，是因为合规下架不能等一轮完整的提案流程（投票延迟 1 天 + 投票期 5 天 + 时间锁 2 天）。

### 4. 审核规则

1. **投稿**：押上押金（`bond`）提交新条目或新版本，登记为待审核。同一条目同一时间只能有一个待审核版本。
2. **投票**：审核员投“通过 / 驳回 / 违规”，哪一方先达到法定票数（`quorum`）就按哪一方结算。法定票数和押金在开审时快照，治理中途改参数不影响进行中的审核。
3. **结算**：
   - 通过：退押金。如果是新条目（第 1 版），作者得到发布奖励和声誉；如果是 Remix，被 Remix 那个版本的作者也得到奖励和声誉。奖励按版本作者发而不是按当前维护者发，因为署名应该跟着内容走。
   - 驳回：退押金。质量问题不罚钱，鼓励尝试。
   - 违规：违规票多于普通驳回票时，押金罚没进金库，并扣作者声誉。适用于抄袭、伪造许可证、恶意代码和垃圾投稿。
4. **回避**：投稿者本人、以及被 Remix 的作者，都不能审核这次投稿。
5. **退出**：没有任何人投票时，投稿者可以撤回；超过审核期仍无结论，任何人都可以关闭审核，押金退回。暂停只挡新投稿，押金永远不会被锁住。
6. **不占位**：第 1 版没有通过的投稿会释放 slug 和内容哈希，改好之后可以重新投。
7. **奖励**：
   - 版本更新只退押金、不发奖励，避免有人靠频繁小改刷奖励。
   - 审核员按参与次数得声誉，而不是按“投对了一方”得声誉，避免跟风。
   - 押金和奖励池在同一个代币余额里，用 `totalBonded` 记账隔离：奖励只能从“余额减押金总额”里发。池子不够时按余额发放，不影响审核结果。不变量测试覆盖了押金账目。

### 5. 代币和声誉分开

声誉不可转让，只能由审核结果产生；代币可以转让，用于投票、押金和奖励。把两者分开，是为了让“对社区的贡献”买不到。将来如果要让声誉参与治理（混合投票），另立决策。

### 6. 内容哈希

`contentHash = sha256(JCS({ manifest, files }))`，JCS 即 RFC 8785 的 JSON 规范化，实现在 `packages/contracts/src/content-hash.ts`。

- 规范化后的结果与键的顺序无关，任何语言都能独立实现并复算。
- 选 sha256 而不是 keccak256，是因为浏览器、Node 和命令行都自带 sha256，复算时不需要装以太坊库。
- 文件内容按原样参与计算，换行由加载器统一成 LF。

### 7. 许可证

- 许可证白名单在链上强制执行。初始值由部署模块从 `@motif/schema` 的 `ALLOWED_SPDX` 生成，保持单一事实来源；之后 DAO 可以调整。
- 社区原创投稿统一按 MIT 授权（进来是什么许可证，出去就是什么许可证），与仓库的许可证一致。目前清单里没有给原创条目写许可证的字段；如果要让原创作者自选许可证，需要给 `ProvenanceSchema` 加字段，届时另立决策。
- 链上登记的是署名和来源，不是所有权。条目代码本来就是开源的：不发 NFT，也不做条目买卖。

### 8. 工具链与工程取舍

- **Hardhat 3.18** 通过 pnpm 安装，测试直接接入 `pnpm verify`，团队成员不需要另装 Foundry 之类的系统工具。另外用到 OpenZeppelin Contracts 5.6.1（MIT）和 forge-std 1.17（只在测试里用）。
- **solc 0.8.34，EVM 目标 cancun**：OpenZeppelin 5.6 的 Governor 依赖的 SignatureChecker 用到了 `mcopy`。以太坊主网和主流 L2 都支持 cancun；部署到其他 EVM 链（例如国内联盟链）之前要先确认。
- **合约不可升级**：登记簿的可信度来自“规则不会被悄悄改掉”。要改规则就部署新合约，由 DAO 迁移角色。
- **时间戳时钟**：L2 的出块间隔不固定，投票期按秒计算才可预期。
- **ABI 导出**：ABI 导出到 `src/generated/abi.ts` 并提交进仓库，站点不需要编译合约就能用；`pnpm test` 会检查这份文件是否过期。
- **一处测试的坑**：测试里的假内容哈希要用 keccak256，不能用 sha256。sha256 是预编译合约调用，写在被测调用的参数里，会抢先消耗掉 `vm.prank` 和 `vm.expectRevert`。

### 9. 默认参数（占位值，全部可以由治理调整）

| 参数 | 默认值 |
| --- | --- |
| 代币总量上限 | 10 亿 MOTIF |
| 创世分配 | 金库（时间锁）6 亿，创世流通 1 亿，奖励池 100 万；其余约 2.99 亿未铸造，留给治理增发 |
| 投票延迟 / 投票期 | 1 天 / 5 天 |
| 提案门槛 / 法定人数 | 100 万 MOTIF / 4% |
| 晚到法定人数延长 / 时间锁延迟 | 1 天 / 2 天 |
| 投稿押金 / 法定票数 / 审核期 | 100 MOTIF / 2 票 / 7 天 |
| 发布奖励 / Remix 奖励 | 1000 / 200 MOTIF |
| 声誉：发布 / 被 Remix / 每次审核 / 违规扣除 | 10 / 5 / 1 / 20 |

这些数字只是为了让系统能跑起来，经济设计需要单独做。

有一点要注意：法定人数按代币总供应量计算。金库里的 6 亿算在分母里，但时间锁不会投票，所以 4% 的法定人数（约 2800 万）实际上相当于 1 亿创世流通份额的约 28%。设计分配方案时要一起考虑。

### 10. 站点接入

1. **链上状态在服务端折叠成视图。** `@motif/contracts` 的 `applyCommunityEvents` 是纯函数：按区块顺序把四个合约的事件折叠成条目、版本、审核、资料、角色和提案。
   - 站点进程里按区块增量同步（`apps/web/src/lib/community/state.ts`），两次同步至少间隔 1 秒；同步失败后退避 15 秒，链停了不会让每个请求都等超时。
   - 状态挂在 `globalThis` 上，整个进程只有一份：Next 的生产构建把页面和接口路由分开打包，模块级变量会各有一份，接口里同步到的区块页面看不到。
   - 每次同步先核对上次同步到的区块哈希，本地链重启或重组时整份重建。
   - 浏览器发完交易后调用 `/api/community/sync` 等服务端追上那个区块，再刷新页面，用户马上看到结果。
   - 集成测试拿真实部署的全部事件折叠，逐项和合约读数对照。
   - 单进程、历史不长时够用；生产环境（多实例、历史很长）要换成独立的索引服务写数据库，接口不变。
2. **源码托管与防抢跑。**
   - 投稿源码按“内容哈希 / 上传者”存放，上传时验证上传者对内容哈希的钱包签名（`uploadMessage`，EIP-191，同时支持合约钱包的 ERC-1271）。
   - 站点只为“链上作者 = 上传者”的版本提供源码和预览产物，下架的条目不提供。抢先把别人的哈希登记上链的人拿不出源码，审核员会判违规。
   - 审核意见、下架理由、创作者资料是按 sha256 寻址的小段文字，被链上引用之后才对外提供。
   - 下架的条目在所有地方都不再提供源码、预览产物和标题，记录页只显示 slug 和链上记录。
   - 只有链上登记的 slug 和清单里的 slug 一致时，作品才算上架。否则有人直接调合约，把链上 slug x 配上清单 slug y，`/skill/motif-x` 就会以 y 的名义分发 x 的代码。
   - 资料 JSON 在读取时再校验一次（只认 http(s) 链接），因为资料哈希可以绕过站点直接写进合约。
   - 目前存在本地 `.data/community/`（不进版本库）；生产环境替换 `storage.ts` 为对象存储即可。
3. **编译放在子进程里。** Next 打包不了 esbuild 和 Tailwind 的原生模块（`serverExternalPackages` 对指向源码的工作区包不起作用），所以站点 fork 一个常驻的编译进程（`packages/compiler/src/worker.ts`），经 IPC 调用。
   - 编译占用的 CPU 不阻塞站点的请求；30 秒超时就杀掉进程，下次请求再起一个。
   - 投稿用的检查器、编译器和市场条目完全相同：能投上去，就等于能在市场里正常运行和导出。
   - **条目 CSS 不可信。** 编译器在调用 Tailwind 之前就拒绝 `@import`、`@plugin`、`@config`、`@source`、`@reference`，以及转义过的 at 规则名。这些指令会让 Tailwind 读服务器上的文件（解析错误还会把文件内容带回给请求方）或执行插件代码。
   - 上传接口先验签名，再编译：签名验证便宜、编译昂贵。
   - 编译队列最多 8 个，超出返回 503；投稿相关接口按 IP 限流（站点进程内，见上线手册）。
4. **钱包只用 viem。**
   - 通过 EIP-6963 发现浏览器钱包扩展（没有时退回 `window.ethereum`）。
   - 不接 WalletConnect：它依赖外部中继服务，国内不稳定，也违反“不依赖外部服务”的原则。
   - 交易先本地模拟，合约的自定义错误翻译成文案再提示，不浪费 gas。
5. **社区作品就是市场条目。**
   - 审核通过、没被下架的社区作品出现在市场列表里（卡片标“社区”）。详情页 `/community/works/<slug>` 和目录条目共用同一个组件，一样有预览、调参、代码、安装、Skill，另多一个“链上记录”标签。
   - shadcn registry（`/r/<slug>.json`）和 Skill（`/skill/motif-<slug>.md`）按默认参数现场生成。
   - 目录条目的详情页 `/market/<slug>` 仍然在构建时静态生成。社区作品放在单独的路由，是因为静态生成的路由运行时不能再变成按请求渲染（Next 会报 `DYNAMIC_SERVER_USAGE`）。
   - 社区作品没有预先录制的海报和循环视频，卡片用标题占位图。投稿通过后自动截图需要在服务端跑浏览器，留到部署阶段再做。
6. **“链上已验证”在浏览器里算。** 详情页把页面上的源码在浏览器里重算内容哈希，再和链上登记的版本比对，不信任站点给的任何结论。
7. **社区投稿可以整合 `sources/sources.json` 之外的上游。**
   - 登记表是维护者整合时用的白名单；社区投稿的上游许可证由审核员核实，检查器把“未登记来源”降级成提醒。
   - 许可证本身仍然必须在白名单里，链上会再校验一次。
8. **本地开发与测试。**
   - `pnpm dev:chain` 启动本地链（每次都是空链）、全新部署并导入目录，开发模式的站点自动连上；本地链提供水龙头（1 ETH + 1000 MOTIF）。
   - 本地节点除了有交易就出块，每秒也出一个空块：否则链空闲时按“上一秒”计票的治理合约读到的永远是旧时间点，刚委托完就发提案会被拒。
   - 端到端测试在 8546 起一条独立的链（部署记录 `ignition/deployments/e2e`），用一个把签名和交易转发给本地节点的测试钱包跑完整流程。
9. **作者工具。** `pnpm item:pack` 把条目目录打包成 `.motif.json`（打包结果一律是 published），`pnpm item:unpack` 还原，`pnpm item:remix` 复制一个条目并记下 `provenance.basedOn`。还原和 Remix 出来的目录是 draft，编辑期间不会出现在本地市场里。

## 风险与未决事项

1. **监管风险，最重要。** 在中国大陆，代币发行融资和虚拟货币相关业务活动属于被禁止的非法金融活动。依据是 2017 年人民银行等七部门《关于防范代币发行融资风险的公告》和 2021 年十部门《关于进一步防范和处置虚拟货币交易炒作风险的通知》。代币上线前需要拿到法律意见，通常要由境外主体运营，并限制大陆用户参与。
   - 合约已经把代币设计成可拆卸的：`Registry` 和 `Identity` 不依赖代币；把 `Curation` 的押金和奖励设为 0，剩下的就是纯粹的登记加审核系统。
2. **内容审核义务。** 站点仍然是内容的展示方，必须保留下架能力（版主角色，加上站点不展示）。链上记录删不掉，所以链上不放任何可读的内容，只放哈希。
3. **部署链未定。**
   - 候选是以太坊 L2（Base、Optimism、Arbitrum 等）或兼容 EVM 的联盟链。
   - RPC 要自建，或者用国内能访问的服务，以符合“不依赖外部 CDN”的原则。
   - 部署前要确认目标链支持 cancun。
4. **经济设计。** 代币分配方案和奖励数额都是占位值。
5. **治理冷启动。** 投票权需要委托后才生效；创世流通份额怎么分发还没定。
6. **审核员女巫攻击和合谋。** 审核员由 DAO 任命、可以撤换，所有投票都在链上，可以审计。审核员名单够大之后，可以考虑随机分配审核员。
7. **安全。** 上线前需要外部审计。合约不可升级，发现漏洞只能靠部署新合约迁移。
8. **投稿抢跑。** 投稿交易进入内存池时，内容哈希和 slug 是公开的，别人可以抢先用同样的哈希投稿，把署名占走。缓解办法有三层：
   - 站点只接受钱包签名的源码上传，并且只为“同一个地址上传、同一个地址上链”的哈希提供源码。抢跑者拿不出源码，审核员会判违规并罚没押金。抢跑者的投稿被驳回后，内容哈希释放，原作者可以重新投。
   - 押金让这种骚扰有成本。
   - 主流 L2 由排序器出块，没有公开内存池，抢跑本身也更难。
   
   如果这些还不够，可以在 `Curation` 里加“提交承诺、再揭示”的两步投稿，代价是多一笔交易。
9. **站点侧的生产化。**
   - 事件索引换成独立服务加数据库，源码存储换成对象存储。
   - 给投稿和托管文字的接口加限流。
   - 社区作品通过后自动生成海报和循环视频。
   - 公开 RPC 的选择。

   见 `docs/PLAN.md` 的社区阶段。

## 实测

- 部署后的字节码大小：Governor 17.7 KB、Curation 11.1 KB、Token 7.7 KB、Registry 7.6 KB、Timelock 6.6 KB、Identity 5.3 KB，都在 24 KB 上限以内。
- gas（`hardhat test solidity --gas-stats`）：
  - 投稿 `submit` 约 34 万；
  - 投票 `vote` 中位数约 11 万，最高约 24 万（结算 Remix 时要发两份奖励）；
  - 注册资料 `register` 约 12 万；委托投票权 `delegate` 约 10 万；
  - 治理流程：发起提案 9 万、投票 12 万、排队 17 万、执行 18 万。
  - 按主流 L2 常见的 gas 价格粗估，每笔大约是 1 美分的量级；实际费用取决于部署链和当时的价格，定链之后再实测。
- 合约包测试（`pnpm --filter @motif/contracts test`，共 106 个）：
  - 81 个 Solidity 测试，含模糊测试 256 轮、押金不变量测试 128 轮 × 64 次调用；
  - 5 个部署集成测试：用真实的 Ignition 模块部署、移交权限、导入真实条目，再走一遍投稿到奖励的流程；
  - 4 个事件索引集成测试：在真实部署上做导入、注册、投稿通过、Remix 违规、下架、提案执行，再把全部事件折叠成状态，逐项和合约读数对照；
  - 16 个单元测试：JCS 格式、手写向量交叉核对、现有 123 个条目哈希两两不同。
- 站点单元测试 11 个：投稿检查（编译子进程的结果和合约包的内容哈希一致）、托管文字校验、提案解码、格式化。
- 端到端测试：社区 3 个用例跑在独立的本地链上，用真实签名和交易：
  - 目录条目显示链上验证；
  - 作者领币、注册资料、投 Remix，两位审核员通过，作品带着链上验证和实时预览进入市场；
  - 委托、提案、投票、排队、执行，任命新的审核员。

  加上原有用例共 140 个，全部通过。
- 本地链上导入 123 个条目（246 笔交易）用时 4.7 秒；投稿预检第一次编译 0.33 秒（启动编译进程），之后约 0.01 秒。
